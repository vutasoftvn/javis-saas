# ADR 008: Next-Best-Action — Boundary Between Four Existing Implementations

## Status
Accepted

## Context
While integrating the COSA Startup Co-founder Methodology (`docs/architecture/COSA_STARTUP_METHODOLOGY_INTEGRATION_ANALYSIS.md`), an audit surfaced **four independent "next best action" implementations** in the codebase, none aware of the others:

1. **`backend/core/strategy/next_action.py`** (`NextActionCandidate`, `NextActionRanking`) + **`backend/app/founder_os/strategy/next_best_action_service.py`** (`NextBestActionService`): a CEO-wide, multi-source candidate generator (GateDecision HOLD, negative PESTEL risk, high-risk Hypotheses, StageTransitionAudit gaps, draft TOWS options) with a 3-round ranking system (R0 deterministic, R1 rules, R2 optional AI rerank). Exposed via REST at `/api/v1/next-actions/ceo/next-actions` (`backend/app/founder_os/strategy/next_action_router.py`) and covered by `backend/app/tests/test_next_best_action_service.py`.
2. **`backend/app/founder_os/validation/review_service.py::synthesize_single_next_best_action`**: a single deterministic recommendation derived by walking one project's validation chain (highest-risk `ValidationAssumption` → missing `ValidationHypothesis` → missing `ValidationExperiment` → missing `ValidationEvidence`). Exposed at `/projects/{project_id}/validation/next-best-action`.
3. **`backend/app/workforce/orchestrator/cosa_cofounder_service.py::CosaCofounderService.get_next_best_action`**: a separate implementation (including hard-coded "genesis" recommendations when no project exists yet) backing `/cofounder/top3`.
4. Three frontend widgets, only one of which was reachable from any route: `NextActionsPanel` (`frontend/lib/modules/hologram_hub/presentation/widgets/next_actions_panel.dart`, consumed system #1's REST shape) and `NextBestActionsCard` (`frontend/lib/modules/hologram_hub/widgets/next_best_actions_card.dart`, generic/unowned) were both **not imported anywhere in the app** — dead code. `Top3FocusWidget` (consuming system #3 via `CoFounderApiService.getTop3Focus()`) **is** wired into `HologramHubView`, which is reachable from `dashboard_view.dart`. `ProjectValidationCard` (`frontend/lib/modules/hologram_hub/widgets/project_validation_card.dart`, consuming system #2 among other validation data) was also not imported anywhere.

An initial plan to "pick one canonical system and delete the other three" (system #3 kept, #1 and #2 deleted) was aborted mid-implementation after discovering system #1 (`NextBestActionService`) is **not dead code**: it is actively called by `backend/app/workforce/chat/chat_execution_service.py` (injects a "Next Best Actions" summary into the main chat AI's prompt context) and registered as a callable tool in `backend/app/integrations/realtime/tools.py` (voice/realtime AI). Deleting it would have broken live conversational AI functionality. The router mount removal was reverted before merge; no backend code was deleted as a result of that aborted attempt.

## Decision
1. **No backend "next best action" system is retired.** All three remain, because each serves a materially different consumer that would otherwise regress:
   - System #1 (`NextBestActionService`) is the **conversational-context supplier**: it is not a dashboard feed, it is retrieval logic embedded in the main AI chat prompt and in realtime voice tools. Its REST endpoint (`/api/v1/next-actions/ceo/next-actions`) has no live UI consumer today, but the service class itself must not be touched without re-auditing `chat_execution_service.py` and `realtime/tools.py` first.
   - System #2 (validation's `synthesize_single_next_best_action`) is the **single-step validation-loop recommendation**, scoped to one project's assumption→hypothesis→experiment→evidence chain. It has no live UI consumer today (`ProjectValidationCard`, its only frontend caller, is not wired into any screen) but is covered by `test_validation_engine_foundation.py` and is cheap to keep; there is no benefit proportionate to the risk of removing it.
   - System #3 (`CosaCofounderService.get_next_best_action`) is the **only one currently rendered to a founder** (`Top3FocusWidget` inside `HologramHubView`), and stays the de-facto canonical UI-facing surface until a deliberate consolidation project (out of scope here) decides otherwise.
2. **Dead frontend code is removed.** `next_actions_panel.dart` and `next_best_actions_card.dart` are deleted — zero import references anywhere in the app, confirmed twice by independent greps. `project_validation_card.dart` is **kept, not deleted**: despite being unwired, it is a materially richer widget (state vector, risk matrix, solution-bias warning, problem scorecard, role coverage, plus a next-best-action row) that substantially matches the Co-founder State Snapshot concept from the methodology supplement (§23). Deleting it to resolve a next-action naming collision would have discarded unrelated, reusable UI work; the correct fix there is narrower (drop or repoint its `getNextBestAction()` call if system #2 is ever retired) and is left for whoever wires this widget into a screen.
3. **No new "next best action" system may be created** for the methodology integration. Any UI that needs a CEO-wide feed should call system #3 (`/cofounder/top3`) since it is the one already live; any UI that needs a single validation-loop recommendation should call system #2; nothing should call system #1's REST endpoint from new UI without first confirming with whoever owns `chat_execution_service.py`/`realtime/tools.py` that doing so is intended (it is currently a backend-internal dependency, not a public-facing feed).
4. Consolidating three backend systems down to one is a legitimate future goal but is a separate, deliberate project — it requires tracing every consumer (chat prompt injection, realtime tool registration, three REST endpoints, whatever frontend eventually wires `ProjectValidationCard`) before removing anything, not a same-session decision made from an incomplete audit.

## Consequences
- Founders continue to see next-action recommendations exactly where they do today (`Top3FocusWidget` in HologramHub, and implicitly via chat/voice AI context) — no regression.
- Two genuinely dead frontend files are removed, reducing surface area without risk.
- Future methodology integration work (Question Graph, ADK↔validation bridge) must route any new "what should the founder do next" UI through system #3, and must not silently reintroduce a fifth implementation.
- This ADR also serves as a cautionary record: an initial audit (subagent-assisted) incorrectly reported system #1 as dead and system #2 as "actively used", both wrong in different directions. Any future consolidation attempt must re-verify consumers directly (grep for the service/model class name across the *entire* backend, not just the module it lives in) rather than trusting a single pass.
