# ADR 009: Bridging the ADK Co-founder Orchestrator and the Validation Interview Loop

## Status
Accepted

## Context
The methodology integration analysis (`docs/architecture/COSA_STARTUP_METHODOLOGY_INTEGRATION_ANALYSIS.md`) flagged that `AdkCofounderOrchestrator` (mission control, specialist delegation) and `ValidationInterviewService` (`/validation/chat`, the discovery/epistemic-classification loop) are fully disconnected — no shared session model, no cross-references, and the frontend has two separate, unbridged surfaces for them. Founders have no single "chat with your co-founder" screen; they must know to navigate to Validation Studio for discovery and to Mission Control for task delegation.

Investigating further to design a fix surfaced a third relevant system: `backend/app/workforce/chat/chat_execution_service.py`, a general-purpose chat backend (`/chat/{brain_id}/sessions/...`) that **is already the live, general "talk to your AI" surface** embedded in `HologramHubView` (via `hub_chat_mixin.dart`/`chat_service.dart`). It runs its own LLM loop with a governed, dynamically-resolved tool registry (`app.core.tool_registry`, populated by `app.core.tool_bootstrap.load_all_tools()`). Critically, that registry has an explicit, deliberate design constraint documented in `company_tools.py`: **no write tools**. The chat AI can only read company data; anything that would change state must go through `chat.propose_action` (`app/workforce/chat/proposal_tools.py`), which files a plain-text item into the existing "Cần bạn xử lý" (NeedsYouItem) queue for a human to act on — the tool call itself never executes the action.

Given this, neither `orchestrate_mission()` (which creates and runs a full mission — plan, specialist delegation, execution — a write/execute action) nor `ValidationInterviewService.process_user_turn()` (which writes `StructuredClaim`/`ValidationAssumption` rows directly, under its own accepted governance model for an explicitly-opened interview session) can simply become auto-invoked tools in the general chat without violating this existing read/write boundary or duplicating governance logic.

## Decision
The bridge is **not** a new merged session model, not a new node inside the ADK `Workflow` graph, and not a new chat UI. It is:

1. **Validation state becomes visible in the one live chat surface via a new read-only tool.** `backend/app/founder_os/validation/validation_tools.py` registers `validation.get_snapshot` (namespace `validation`, tool `get_snapshot`) in the canonical tool registry, following the exact pattern of `app/founder_os/strategy/tools.py` and `app/business/sales/sales_tools.py` (`@register(..., permission_level="read_only", risk_level="low", allowed_agent_keys=["chief_of_staff"])`). It composes `ValidationEngineService.get_state_vector`, `RiskPrioritizationService.get_riskiest_assumptions`, `ValidationReviewService.synthesize_single_next_best_action`, and `ProblemIntelligenceService.evaluate_role_coverage` into one summary (project stage, per-dimension confidence, top risk assumption, next-best-action, interview role coverage) — the same data `ProjectValidationCard` renders, reshaped for an LLM tool response. This means a founder chatting in the existing HologramHub chat can ask "where are we on validating X" and get a real answer without leaving the conversation, and the AI can then say "let's continue the discovery interview in Validation Studio" as a pointer rather than trying to run the interview inline.
2. **Mission dispatch needs no new code.** `chat.propose_action` already covers "the AI thinks a mission/task should start" — it creates a NeedsYouItem the founder reviews and acts on. This is intentionally descriptive-only today (approving the item does not itself call `orchestrate_mission()`); wiring an approved proposal to auto-execute a mission is a separate, larger change to the NeedsYouItem/approval-queue system, not something this methodology integration should bolt on. It is out of scope here and left as a known follow-up if wanted.
3. **`ValidationInterviewService`'s write path stays exactly as-is**, reachable only through its own `/validation/chat` session with its own accepted governance model (founder explicitly opens an interview). It does not become a general-chat tool because doing so would mean either (a) silently writing to the validation chain from a read-only-by-design chat loop, or (b) rebuilding its governance under `propose_action`'s per-call approval flow, which would break its multi-turn conversational nature (every extracted claim would need individual human approval, defeating the point of an interview).
4. No changes to `AdkCofounderWorkflow` (`adk/workflow.py`) or its nodes — the mission pipeline is unaffected.

## Consequences
- Founders get a materially better "one co-founder" feel from their *existing* chat screen without any new screen, new session concept, or governance exception: they can ask about validation status inline, and the AI can point them to the right dedicated surface (Validation Studio for discovery, NeedsYouItem queue for mission approval) instead of silently acting for them.
- No migration, no new tables, no new frontend module. The only new backend artifact is `validation_tools.py` (one tool) plus its registration line in `tool_bootstrap.py`.
- This is intentionally a partial bridge — it gives visibility, not unification of the three systems' execution paths. A future, deliberate decision to let approved `propose_action` items auto-execute (including auto-starting a mission or opening an interview session) is possible but is its own project with its own risk review, not something decided by this ADR.
- Precedent: `founder_os/strategy/tools.py` explicitly warns against attaching an unseeded `flag_key` to a chat tool, citing `company.next_best_actions` having silently disappeared that way. `validation_tools.py` follows that warning and registers without a `flag_key`.
