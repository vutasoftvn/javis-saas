# ADR 007: Strategy Evidence Ladder vs Validation Chain — Ownership Boundary

## Status
Accepted

## Context
Two epistemically-similar concept pairs exist in the codebase with overlapping names:

- `backend/core/strategy/evidence.py`: `Hypothesis` / `Evidence`, using an evidence ladder (E0–E6), `hypothesis_refs`, `experiment_refs`, `artifact_refs`.
- `backend/core/validation/evidence_chain.py`: `ValidationAssumption` → `ValidationHypothesis` → `ValidationExperiment` → `ValidationEvidence` → `ValidationReview` → `ValidationDecision`, an epistemically structured chain (`EpistemicType`, `AssumptionStatus`, `ReviewVerdict`, `FounderDecisionEnum`).

This overlap was flagged while integrating the COSA Startup Co-founder Methodology (`docs/architecture/COSA_STARTUP_METHODOLOGY_INTEGRATION_ANALYSIS.md`), which needs a single, unambiguous place to write assumption/hypothesis/evidence data generated by the new Question Graph engine. Without a documented boundary, future features risk writing the same kind of fact into two different tables depending on which module the author happened to be in — the exact "duplicate architecture" failure mode `CLAUDE.md` §14 and the canonical ownership map warn about.

## Decision
1. **`core.validation` evidence chain (`ValidationAssumption`→...→`ValidationDecision`) is the canonical store for startup experimentation truth**: founder-stated claims, testable hypotheses, experiments run to test them, evidence gathered, AI/human review of that evidence, and the founder's resulting decision. This is what the Co-founder Operating Loop (Classify → Challenge → Ask → Structure → Test → Review → Decide) reads and writes. The Question Graph engine (Phase 2 of the methodology integration) writes exclusively into this chain.
2. **`core.strategy.evidence` (`Hypothesis`/`Evidence`, evidence ladder E0–E6) remains the store for strategic/contextual claims** that are not part of a single experiment's assumption→decision lifecycle — e.g. PESTEL signals, competitive-landscape claims, macro market evidence referenced by multiple initiatives at once. It is not being retired or merged into the validation chain.
3. New code must pick one chain based on this rule: *if the fact is produced by testing one specific assumption through one specific experiment, it belongs in the validation chain; if it is a standing contextual claim referenced by strategy/PESTEL/competitive work, it belongs in `core.strategy.evidence`.* When in doubt, prefer the validation chain — it is the one wired into stage gates (`StageTransitionAudit`), next-best-action generation, and the co-founder orchestrator.
4. No new `Hypothesis`/`Evidence`-shaped table is to be created for methodology work going forward; both existing chains are reused as-is per this boundary.

## Consequences
- The Question Graph engine and the ADK Classify/Challenge/Ask node (methodology integration Phase 2–3) have an unambiguous write target: the `core.validation` chain.
- `core.strategy.evidence` keeps serving PESTEL/competitive/strategic-context use cases without needing a migration.
- Future reviewers can resolve "which table do I write to?" questions by referring to this ADR instead of re-litigating the overlap.
- If a future need arises to unify these two chains (e.g. cross-referencing a strategic evidence item from a validation experiment), that requires a new ADR — this document does not authorize such a merge.
