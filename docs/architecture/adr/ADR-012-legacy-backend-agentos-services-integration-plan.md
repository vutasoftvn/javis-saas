# ADR-012: Integration plan for `legacy/backend` vs `agentos/` + `services/` before Frontend cutover

## Correction (2026-08-22, same day, after initial publish)

The original version of this ADR stated `legacy/backend` was "the only one actually serving traffic today." That claim has been **disproven** by direct inspection: the most recent commit on `main` (`5c5bc85`, "restructure and consolidate AgentOS root architecture...") renamed the repo-root `backend/` directory to `legacy/backend/` **and split its agent-runtime code out to a separate sibling `legacy/agent_runtime/` (containing `workforce/`, `cosa_core/`)** — but did not update `docker-compose.yml` or `legacy/backend/Dockerfile.api` to match:

- `docker-compose.yml` still referenced `context: ./backend` (6 occurrences) — a path that no longer exists at all (`git ls-files | grep '^backend/'` → 0 files). **Fixed in this pass** — all 6 references now point at `./legacy/backend`.
- `legacy/backend/Dockerfile.api` runs `pip install -e ./cosa_core`, and at least 10 production files under `legacy/backend` (`integrations/llm_providers/*`, `integrations/workflows/n8n_gateway_service.py`, `integrations/workflows/runtime/runner.py`, `integrations/devices/router.py`, `db/base.py`, 2 scripts) import `workforce.*` or `cosa_core.*` directly — packages that now live in `legacy/agent_runtime/`, **outside** `legacy/backend`'s Docker build context. This means `brain-api`, `agent-worker`, and even the `migrate` service (whose `alembic upgrade head` needs `db/base.py`, which imports `cosa_core`) **cannot currently build or run** via the root `docker-compose.yml`, even after the path fix above. **Not fixed in this pass** — resolving it means deciding whether `legacy/agent_runtime` should be merged back under `legacy/backend`, or the Dockerfile/build process should be changed to pull from both directories; that is an architecture call for the user, not something to guess at.

**Practical consequence:** as of this ADR, *no backend is confirmed runnable end-to-end via documented tooling* — `legacy/backend` is currently broken at the infra level (not just "missing capabilities" as originally stated), and `agentos/`+`services/` are inert/unconsumed (see below). The rest of this ADR's reasoning (keep `legacy/backend`'s integrations as the reused source of truth, adapt via `agentos/` rather than fork) still holds — it just needs the build to actually work first.

### Correction #2 (same day, after attempting the Docker fix) — the split is 6-way, not 2-way

Attempting to actually build `brain-api` (`docker compose build brain-api`, then `docker run ... python -c "import workforce, cosa_core, agent_runtime"`) surfaced more: `legacy/` is not `backend` + `agent_runtime`, it is **six** sibling directories — `legacy/backend`, `legacy/agent_runtime` (`workforce`/`cosa_core`/`agent_runtime`), `legacy/platform` (`core`/`platform_core`), `legacy/business` (`business`/`business_core`), `legacy/domains` (`regulations`/`founder_os`), `legacy/entrypoints` (`worker_main.py`/`full_main.py`/`central_main.py`). A static import scan of `legacy/backend` alone found **39 additional cross-directory top-level imports** beyond `workforce`/`cosa_core`/`agent_runtime` (e.g. `from core.snowflake import ...` → `legacy/platform/core`).

This split traces to an **earlier, narrower, already-completed refactor**: `docs/superpowers/plans/2026-08-21-self-host-app-factory.md` ("Quyết định 3") introduced `backend/app/full_main.py` / `central_main.py` with `backend/app/main.py` kept as a thin backward-compatible alias (`from full_main import app`), explicitly scoped to **not** touch the root `docker-compose.yml`. That plan's `backend/app/` was a single directory containing `app`, `workforce`, `cosa_core`, `platform`, `business`, `domains`, `entrypoints` as subdirectories. The later `5c5bc85` restructure (2026-08-22) then split *those* subdirectories out into six top-level `legacy/*` siblings — consistent with clearing the way for `agentos/`+`services/` — but never updated the Dockerfiles or root `docker-compose.yml` to match, and (per this ADR's evidence) `agentos/`+`services/` are not yet capable of replacing what was split out.

`legacy/backend/Dockerfile.api`/`Dockerfile.worker` and the root `docker-compose.yml` were updated in this pass to build from the repo root and `COPY` in `workforce`/`cosa_core`/`agent_runtime` (verified: image builds successfully) — but this is **known-incomplete**: at least `core`/`platform_core` (from `legacy/platform`), `business`/`business_core` (from `legacy/business`), and `regulations`/`founder_os` (from `legacy/domains`) are also imported and are not yet copied in. Fully reconstituting the merged monolith inside the image is a materially bigger job than "fix a Dockerfile path," and it is not obviously the right goal — the alternative is to formally treat `legacy/backend` as retired/read-only and extract *only* the specific pieces `agentos/` needs (LLM provider clients, OAuth flow, n8n gateway, sandbox wiring) as this ADR's Decision already outlines, rather than resurrecting the whole six-way-split monolith.

### Follow-up: LLM Chat Gateway delivered self-contained (2026-08-22, later same day)

This ADR's original Decision §1 said the LLM Gateway adapter should call `legacy/backend`'s already-running gateway over HTTP rather than reimplement the 7 provider clients. That assumed `legacy/backend` would run. Since Correction #2 froze it instead, `agentos/core/adapters/model_gateway.py` was built as a **self-contained** multi-provider `ModelProvider` factory (`agentos/core/adapters/{openai_compatible_provider,anthropic_provider,model_gateway}.py`) — DeepSeek (existing harness adapter), OpenAI, OpenRouter, Anthropic — using `httpx` directly against each provider's public API, with no import of `legacy/backend` at all. Covered by unit tests (`tests/agentos/core/test_{openai_compatible_provider,anthropic_provider,model_gateway}.py`) using `httpx.MockTransport`, no live network calls. Gemini/Kira AI/apiai_vn are not ported (lower priority, add later following the same pattern in `openai_compatible_provider.py` where the provider is OpenAI-compatible).

**Sandbox execution, OAuth, n8n, Memory (PgVectorMemoryStore), and Extensions were not attempted in this pass — paused by user decision, not abandoned.** Each hits a different real blocker, verified rather than assumed:
- **Sandbox**: `docker compose --profile sandbox up opensandbox` fails — the image `opensandbox/server:0.2.2` does not exist on Docker Hub (`failed to resolve reference`). This service has apparently never actually been runnable; the wire protocol cannot be tested against anything real.
- **OAuth / n8n**: need DB-backed state (`AutomationRun`, OAuth tokens) that only exists via `legacy/backend`'s Alembic migrations, which don't run since it's frozen.
- **Memory (`PgVectorMemoryStore`)**: the `agent_memories` table it queries (`agentos/memory/pgvector_store.py`) has **no migration anywhere in the repo** — `grep -rl "agent_memories"` matches only that one file. Wiring this isn't "connect an existing thing," it's "author a new schema and decide who owns migrations for `agentos`-native tables" — a real scope decision, not a quick fix.
- **Extensions**: no `services/` cluster owns this API yet (unchanged from the original finding).

Guessing at any of these without the ability to test end-to-end risks shipping adapters that look complete but silently don't work. Next session should start by deciding which of these four to unblock first (each needs a different kind of fix: rebuild/replace the sandbox image, write a new agentos memory migration, or accept OAuth/n8n/Extensions stay parked until `legacy/backend`'s fate or a `services/` owner is decided).

### Follow-up: idempotency gap found and fixed for one endpoint (2026-08-22, later same day)

Cross-checking `services/` against the blueprint's §82 ("Tool business write cần idempotency key") found that `operating.tasks` already had an `idempotency_key` column with a `UNIQUE (workspace_id, idempotency_key)` constraint (`services/operations/migrations/1_create_tasks.up.sql`) that **`createTask` never used** — `CreateTaskParams` didn't accept it and the INSERT never wrote it, so the safety mechanism the schema already paid for was dead. Fixed: `CreateTaskParams.idempotencyKey?: string`, INSERT now sets it, `ON CONFLICT (workspace_id, idempotency_key) DO UPDATE SET id = operating.tasks.id RETURNING ...` (the standard Postgres "return-existing-row-on-conflict" idiom) so a retried create with the same key returns the original task instead of inserting a duplicate. Verified against the real Postgres test DB via `encore test` (2 new tests in `services/operations/task.test.ts`, full suite 114/114 pass, `tsc --noEmit` clean) — not just type-checked.

**Scope note:** only `operations.tasks` had this column — `commercial` and `finance-legal` cluster tables (leads, opportunities, transactions, etc.) had no `idempotency_key` column at all, so the same fix needs a new migration per table, not just a code change.

**Second endpoint fixed (2026-08-22, later same day):** `finance.financial_transactions` (`recordFinancialTransaction`, `services/finance-legal/financial-transaction.ts`) was the highest-stakes remaining case — a retried agent write here means an actual duplicate charge, not just a duplicate row. Added migration `services/finance-legal/migrations/7_add_transaction_idempotency_key.up.sql` (new `idempotency_key` column + `UNIQUE (workspace_id, idempotency_key)`), same `ON CONFLICT ... DO UPDATE SET id = id RETURNING ...` pattern as `task.ts`. Verified against real Postgres: full `services/` suite 115/115 pass (was 114; +1 new test in `financial-transaction.test.ts`), `tsc --noEmit` clean.

**Still not done** (documented, not silently skipped): `commercial.leads`, `commercial.opportunities`, `commercial.accounts`, `commercial.contacts`, `finance.accounting_periods`, `finance.legal_obligations`, `finance.legal_checklist_items`, and `operations`'s OKR/12WY/initiative create endpoints all still lack an `idempotency_key` column. Same pattern applies to each (migration + `CreateXParams` field + `ON CONFLICT` in the INSERT) — mechanical but needs one migration per table, left for a dedicated pass rather than rushed through here.

**Migrations staged, not yet wired (2026-08-22, later same day):** `services/commercial/migrations/6_add_idempotency_keys.up.sql` (accounts, contacts, sales_leads, sales_opportunities) and `services/finance-legal/migrations/8_add_more_idempotency_keys.up.sql` (accounting_periods, legal_obligations, legal_checklist_items) were added — the schema is ready — but the corresponding `.ts` create endpoints were **not** updated to accept/use the column yet (unlike `task.ts` and `financial-transaction.ts`, which are fully wired). Verified harmless: full `services/` suite still 115/115 pass with these migrations applied. Wiring the `.ts` side is the next mechanical step, same pattern as the two done endpoints.

### Bigger finding while wiring idempotency: half the `operations`/`finance-legal` agent tools pointed at URLs that don't exist (2026-08-22, later same day)

While checking `services/operations/twelve-week-year.ts` to wire `twelve_wy_score_record`'s idempotency key, its route list didn't contain the path that tool was calling at all. Auditing every `agentos/tools/clusters/*.py` handler's literal URL against the real `path:` in the corresponding `services/*/*.ts` route (not just checking it type-checks — checking the string matches a route that's actually registered) found:

| Tool | Called (broken) | Real route | Fix |
|---|---|---|---|
| `okr_cycle_create` | `/operations/okrs/cycles` | `/operations/okr-cycles` | path corrected |
| `okr_objective_create` | `/operations/okrs/objectives` | `/operations/objectives` | path corrected |
| `okr_key_result_update_progress` | `/operations/okrs/key-results/{id}/progress` (body `currentValue`) | `/operations/key-results/:id/checkin` (body `value`) | path + body key corrected |
| `twelve_wy_plan_create` | `/operations/twelve-week-year/plans` | `/operations/cycles` (the 12-week "plan" *is* the cycle entity) | path corrected |
| `twelve_wy_score_record` | `/operations/twelve-week-year/scores` | **no such endpoint exists anywhere** — `WeeklyPlan.executionScore`/`outcomeScore` columns exist but no API writes them | **tool removed**, not redirected — there's nothing real to redirect it to; adding the missing endpoint is a new feature, not a path fix |
| `accounting_period_create` | `/finance-legal/accounting/periods` | `/finance-legal/accounting-periods` | path corrected |
| `legal_obligation_create` | `/finance-legal/legal/obligations` | `/finance-legal/obligations` | path corrected |
| `legal_obligation_list` | `/finance-legal/legal/obligations` (GET) | **no list-by-workspace endpoint exists** — only `POST /obligations`, `GET /obligations/:id`, `POST /obligations/:id/fulfill` | **tool removed**, same reasoning as above |
| `legal_checklist_create` | `/finance-legal/legal/checklists` | `/finance-legal/checklist-items` | path corrected |

`commercial_tools.py` and `identity_tools.py` were checked too and are already correct — no changes needed there. `task_create`/`task_list`/`task_update_status`/`transaction_record`/`transaction_list`/`initiative_create` were also already correct.

**Why this went undetected:** every existing test for these tools (`tests/agentos/test_encore_tool_bindings.py`, `test_agent_os_full_lifecycle.py`) mocks `EncoreClient` with `AsyncMock(return_value=...)` — it returns canned data for *any* path, so a test asserting "the tool was called with some path" never notices that path doesn't exist as a real `services/` route. `test_agent_os_full_lifecycle.py` even asserted the *wrong* path as if it were correct (`mock_encore.post.assert_any_call("/operations/okrs/cycles", ...)`), which has now been corrected to match the fixed code.

**Fix verified two ways:** (1) 8 new direct tests in `test_encore_tool_bindings.py` pin the exact corrected path per tool (including two asserting the broken tools are no longer registered at all, not silently pointed at a plausible-looking wrong URL); full `tests/agentos` suite now 233/233 pass (was 225). (2) `services/` itself still 115/115 pass + `tsc --noEmit` clean — these were client-side (`agentos/`) bugs only, the server routes themselves were always correct.

**Not fixed (real gap, not a path bug):** `twelve_wy_score_record`'s underlying capability (recording a weekly execution score) has no backing endpoint in `services/operations` at all. Needs a new `updateWeeklyPlanScore`-shaped endpoint (or extending `createWeeklyPlan`) before the tool can be re-added — a small new feature, left for a dedicated pass. Same for `legal_obligation_list` — needs a new "list obligations by workspaceId" endpoint.

### Decision on Correction #2 (user confirmed)

`legacy/backend` is **frozen-in-place, not actively resurrected**. It is not deleted (still a valid read reference for extracting integration logic per this ADR's original Decision §1), but no further effort goes into making its Docker build fully work. Concretely:

- `migrate`, `migrate-control-plane`, `brain-api`, `agent-worker` in the root `docker-compose.yml` are now gated behind `--profile legacy` — `docker compose up` (no profile) starts only what is confirmed working (`postgres`, `minio`, `livekit`, `realtime-agent`, `realtime-agent-cloud`). Running `docker compose --profile legacy up brain-api` will still fail at import time (`core`/`platform_core`/`business`/`business_core`/`regulations`/`founder_os` are not copied into the image) — this is expected and documented, not a regression to chase.
- Effort instead goes toward the extraction path already named in this ADR's Decision §1–3: pull LLM Gateway/OAuth/n8n/Sandbox out as small, adapter-friendly pieces `agentos/` can call, rather than reviving the six-way-split monolith wholesale.
- **A broader lesson this correction surfaced, worth stating explicitly:** several project documents (the ownership map, `services/operations`'s own "Phase 1: done" note, this ADR's own first draft) asserted things were canonical/working/serving-traffic that turned out false the moment they were checked against a real build or a real consumer search. Documentation in this repo is a reliable record of *intent and decisions made*, not a reliable record of *current working state* — treat "canonical production" / "done" claims as needing a build or grep to confirm before relying on them for a new decision, the same way this ADR's corrections were produced.

## Context

A full-repo review (2026-08-22, excluding `frontend/`) found that COSA currently has **three** backend surfaces, not one:

1. **`legacy/backend`** (FastAPI, `backend/workforce/...`, `backend/agent_runtime/...`, `backend/integrations/...`) — the system `docs/architecture/COSA_CANONICAL_OWNERSHIP_MAP.md` still documents as canonical, and the only one actually serving traffic today: it runs as `brain-api`/`agent-worker` via the root `docker-compose.yml`, and owns LLM Gateway (7 providers), Google OAuth, n8n workflow bridge, OpenSandbox execution, and Extensions/Plugin API.
2. **`agentos/`** (Python Agent Core) — per `ADR-AGENTOS-001`, this was introduced explicitly as an **inert, parallel** implementation: "production traffic keeps flowing through `cosa_core`/`workforce`; `agentos/` is inert (no caller wires it into `main.py`) until a later phase explicitly cuts traffic over." That has not changed since.
3. **`services/`** (Encore.ts, 4 clusters) — Phase 1 parity is recorded for `identity`/`operations`/`commercial`/`finance-legal`, but the operations cluster plan itself records: *"No existing consumer calls `services/tasks` or `services/okr` over HTTP today (verified: no references in `backend/`, `frontend/`, or `services/realtime_agent/`)"*. i.e. `services/` is schema/logic-parity-verified in isolation, not yet consumed by anything.

Meanwhile `frontend/lib/core/network/api_client.dart` already defaults its `baseUrl` to the Encore Gateway (`http://localhost:4000`), and `normalizeEndpoint()` already maps legacy-style paths (`/tasks`, `/sales`, `/auth`) onto `services/` routes — a **forward-looking** default written ahead of `services/` actually being wired to real traffic. One screen (`settings_extensions_page.dart`) still hardcodes `http://localhost:8000` (the legacy `brain-api`), the only capability visibly still calling the old system directly.

**Net effect:** nothing today proves `agentos/` + `services/` can serve a real end-to-end business flow (chat → tool call → business write → response) the way `legacy/backend` already does. Connecting `frontend/` now would mean building against a target that is parity-tested in isolation, not integration-tested end-to-end, while several capabilities (LLM chat, OAuth, automation, sandbox, extensions) simply don't exist there yet.

## Decision

1. **`agentos/` + `services/` are the target canonical system.** `legacy/backend` is not retired outright — it is kept running as the **only current source of** LLM Gateway, Google OAuth, n8n bridge, and OpenSandbox execution, accessed by `agentos/` through explicit adapters (HTTP calls to the already-running `brain-api`), not by forking that code into `agentos/`. This avoids a second implementation of security-sensitive OAuth/token-encryption logic and avoids double-maintaining 7 LLM provider clients.
2. **Before `frontend/` is pointed at `services/` as its only backend**, `agentos/` must be able to run at least one real end-to-end business flow (an agent tool call that reaches a `services/` cluster, is policy/approval-gated, and is traced durably) — not just cluster-isolated parity tests. Phase 1 of the accompanying completion plan (executor policy/approval gate + durable trace) is a prerequisite, now implemented (`agentos/core/executor.py`, `agentos/core/trace_sink.py`).
3. **Missing capability families are tracked explicitly** (added to the ownership map below) instead of silently living only in `legacy/backend` with no ownership record: LLM Chat Gateway, OAuth/External Account Linking, Automation (n8n) Bridge, Sandboxed Code Execution, Extensions/Plugin API.
4. `settings_extensions_page.dart`'s hardcoded `:8000` is *not* a bug to silently "fix" by pointing it at `:4000` — `services/` has no Extensions API yet. It stays pointed at `legacy/backend` until an Extensions capability owner exists in `services/` or `agentos/` (see ownership map).

## Consequences

- `legacy/backend` stays running in the root `docker-compose.yml` for the foreseeable future as an internal integration layer, not a deprecated system to delete. README should say so explicitly (see companion doc-cleanup changes) instead of omitting it.
- New `agentos/tools/clusters/` adapters will be added incrementally (n8n bridge, sandbox execution) as separate, reviewed changes — each wrapping the existing `legacy/backend` service rather than reimplementing it.
- `frontend/` should not be treated as "ready to fully cut over to `:4000`" until this ADR's capability list has an owner for every row, and at least one integration test exercises agent → `services/` → back to caller end-to-end (not yet present as of this ADR).
