Đúng. Với thông tin mới là **dự án còn đang dev và database có thể reset hoàn toàn**, mình thay đổi khá mạnh kết luận trước:

> **Không migrate 301 bảng legacy. Không preserve schema legacy. Không tạo “archive DB” để mang nợ tiếp.**
> Ta dùng legacy như **nguồn archaeology để xác định behavior/requirement**, rồi thiết kế lại database từ current runtime. Cái nào current code thực sự dùng thì giữ/port; không có consumer hiện tại thì loại.

Và mình đồng ý với boundary 2 user mà bạn giải thích. Hai bảng user **không phải duplication sai về kiến trúc**, nhưng implementation local hiện tại vẫn cần chỉnh.

# 1. Chốt lại ownership của Identity/Auth

Mô hình đúng nên là:

```text
                    COSA CONTROL PLANE
                ┌─────────────────────────┐
                │ users   ← canonical     │
                │ credentials             │
                │ profiles                │
                │ companies               │
                │ company memberships     │
                │ roles                   │
                │ licenses/entitlements   │
                └───────────┬─────────────┘
                            │
                     authenticate
                            │
                     platform JWT
                            │
                     sync / project
                            ▼
                 COMPANY LOCAL / VPS
                ┌─────────────────────────┐
                │ user_projections        │
                │ workspaces              │
                │ workspace_memberships   │
                │ workforce_members       │
                │ local business DB       │
                └─────────────────────────┘
```

Control Plane hiện đúng là đang giữ `cosa.users`, password hash, profile, company, role/membership, plan, license và entitlement. Đây nên là authentication/tenancy source-of-truth.

Company hiện có một projection tương đối đúng: `workspaces`, `users`, `workspace_members`, `organizations`, `workforce_members`; `platform_user_id` và `platform_company_id` đã có. IDs local cũng đang dùng Drizzle `bigint mode:"bigint"` nên phần precision hiện tại đã được sửa đúng.

Nhưng **local `users` vẫn đang sở hữu `password_hash` và `role`**, hai field này nên bỏ:

```text
company.core.users.password_hash  -> DELETE
company.core.users.role           -> DELETE
```

`role` phải thuộc membership. Password chỉ COSA Control Plane giữ.

Mình thậm chí đề nghị rename:

```text
core.users
    ↓
core.user_projections
```

để developer sau này không hiểu nhầm nó là canonical user store.

# 2. Sync hiện tại đi đúng hướng nhưng có một bug semantic quan trọng

`syncFromPlatformService()` hiện đã làm:

```text
validate platform membership
→ find/create local user
→ find/create workspace
→ create workspace membership
→ issue local JWT
```

Đây chính xác là flow cần thiết.

Nhưng implementation hiện có đoạn:

```text
role = isNewWorkspace ? "admin" : "member"
```

thay vì sync `member.roleId` từ COSA.

Như vậy founder/cofounder/user từ Control Plane có thể biến thành role khác trong Company.

Phải thành:

```text
Control Plane membership
       │
       ├ platform_membership_id
       ├ role_id
       ├ status
       └ version / updated_at
              ↓
Company workspace_membership
       │
       ├ platform_membership_id
       ├ role_id
       ├ status
       ├ source_version
       └ synced_at
```

Và sync không chỉ CREATE. Nó phải **UPDATE role/status/revocation**.

Một local JWT chỉ đại diện cho một projection đã xác minh; nó không trở thành một identity authority thứ hai.

# 19. Trình tự refactor mình sẽ làm nếu triển khai vào repo

1. **Freeze legacy as reference bằng Git tag**, sau đó coi `legacy/*` là removable; không còn yêu cầu runtime compatibility.

2. **Sửa Identity trước**: bỏ Company password/local register-login ownership, rename user projection, membership sync đúng role/status, bỏ `organizations` 1:1, chuẩn hóa workforce member.

3. **Cleanup current DB before reset**: xóa `brain_id`, `mvp_stage_id`, các dangling IDs; chuẩn hóa owner/assignee; chọn Strategy làm canonical validation và xóa `finance-legal.validation`.

4. **Cut frontend khỏi `/workforce/*`**: map feature đang dùng sang Agent API/Company/COSA; feature không còn requirement thì xóa UI/service code thay vì rebuild backend.

5. **Salvage Agent legacy**: viết regression tests cho budget, stuck detection, tool schema, redaction, extension manifest, approval behavior; port những phần thiếu sang `agent`.

6. **Remove runtime dependencies**: bỏ realtime mount legacy, backend PYTHONPATH/env fallback, old Docker/Compose profile, old Makefile/CI `agentos` paths.

7. **Delete legacy code + legacy Alembic**: `legacy/backend`, business/platform/domains, workforce/cosa_core sau khi salvage complete.

8. **Squash migrations thành clean dev baseline rồi reset toàn bộ DB**. Seed chỉ Control Plane roles/plan/dev admin; Company users phải sinh qua `sync-from-platform`, không seed password/local auth.

Với khả năng reset DB, mình nghĩ **đây là thời điểm rất tốt để thực hiện một “schema reset”, không phải “legacy migration”**.

Legacy 300+ tables nên bị coi là một **catalog requirement lịch sử**. Sau audit current consumers, mình thấy phần lớn không đáng tồn tại nữa. Hai thứ legacy còn ảnh hưởng thực tế nhất là **Flutter `/workforce/*` contract** và một số **deployment references**; còn `cosa_core/workforce` chủ yếu có giá trị để salvage behavior, không phải để tiếp tục chạy.

Quan trọng hơn, mình đã thấy schema mới bắt đầu có nguy cơ tái phát bệnh legacy: **Strategy và Validation đang duplicate cùng assumption/experiment/evidence flow**, Company user vẫn có local password, có `brain_id`/`mvp_stage_id` không rõ owner, và actor IDs chưa thống nhất. Đây là những thứ nên sửa **trước lần reset DB kế tiếp**, thay vì để thêm migration chồng lên.

Nếu đi theo hướng này, mình sẽ đặt mục tiêu cuối cùng không phải “301 → 100 tables”, mà là **mỗi table còn lại đều có current code owner và current product reason để tồn tại**.
