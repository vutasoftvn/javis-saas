# 1. Điểm cần sửa lớn nhất: proposal đang hiểu ADK 2.7 chưa đúng

Proposal viết rằng API thật của ADK 2.7 “**KHÔNG phải Graph API**”, rồi đề xuất tự xây root `BaseAgent` với Python orchestration logic.

Điểm này hiện **không còn đúng**.

Ngay source chính thức của `google-adk` tag `v2.7.0` có:

```text
google.adk.workflow.Workflow
        ↓
BaseNode
        ↓
Graph
        ↓
Nodes / Edges / Triggers
        ↓
Concurrent scheduling
        ↓
Replay / Resume
```

Source của ADK 2.7 mô tả thẳng `Workflow(BaseNode)` là “graph-based workflow node”, có graph validation, concurrency, replay và resume từ session events.  Google cũng mô tả ADK 2.0 theo hướng workflow graph deterministic, kết hợp deterministic nodes, LLM agents, routing, HITL và dynamic workflow. ([Google Developers Blog][1])

Vì vậy, với COSA/OPC, mình sẽ **không tự viết một `BaseAgent` để tái tạo lại workflow engine mà ADK đã cung cấp**.

Kiến trúc nên là:

```text
AdkCofounderWorkflow
│
├── CreateMissionNode
├── BuildCompanyContextNode
├── RiskClassificationNode
├── PlanningNode
│
├── Specialist Delegation
│   ├── Sales
│   ├── Finance
│   ├── Marketing
│   └── Legal
│
├── Wait/Resume
├── SynthesisNode
├── ApprovalGateNode
├── ExecutionNode
└── QualityGateNode
```

Phần nào deterministic thì dùng `FunctionNode`/workflow node.

Phần nào cần reasoning thì dùng LLM agent.

Phần nào cần DeepSeek thì **enqueue durable delegation**, không chạy Harness trực tiếp.

Đây chính xác là trường hợp ADK Workflow được thiết kế để giải quyết.

# 2. Không nên để ADK gọi DeepSeek Harness trực tiếp

Proposal có hướng tạo:

```text
adk/execution_tool.py
    ↓
agent_runtime_manager.get_runtime("deepseek_harness")
    ↓
runtime.run()
```

Mình khuyến nghị **bỏ hướng này**.

Codebase hiện đã có một execution pipeline durable tốt hơn:

```text
RunStep
   ↓
TaskBoardService.assign_step()
   ↓
DelegationJob
   ↓
PostgreSQL durable queue
   ↓
delegation-worker
   ↓
InProcessSubagentProvider
   ↓
AgentRuntimeManager
   ↓
DeepSeekHarnessAdapter
```

`TaskBoardService.assign_step()` đã làm khá nhiều thứ mà ADK không nên tự làm lại: locking, tenant verification, dependency check, delegation depth, provider health, permission policy, approval creation, idempotency và event logging.

Worker cũng đã có lease, retry, recovery và `FOR UPDATE SKIP LOCKED`. Đặc biệt, `delegation_loop()` mới là nơi gọi:

```python
await agent_runtime_manager.start()
await delegation_provider_manager.start()
```

rồi mới thực thi runtime.

`InProcessSubagentProvider` ở worker lại dùng:

```python
get_runtime(..., allow_default=False)
```

rất đúng cho production.

Trong khi FastAPI `main.py` hiện **không start `AgentRuntimeManager`**.

Do đó:

```text
SAI

ADK
 ↓
DeepSeekHarnessAdapter.run()
```

nên đổi thành:

```text
ĐÚNG

ADK Workflow
 ↓
Create/Assign RunStep
 ↓
DelegationJob
 ↓
commit DB
 ↓
Workflow pause
    ...
delegation-worker
 ↓
DeepSeek Harness
 ↓
terminal result
 ↓
enqueue/resume ADK Mission
```

Lợi ích rất lớn: process crash, VPS restart hoặc DeepSeek mất mạng cũng không làm mất mission.

# 3. Phải phân biệt rõ “Tool” và “Job”

Đây là một refinement mình rất muốn thêm vào proposal.

Hiện proposal hơi gom mọi capability thành “tool”. Thực tế OPC nên có hai primitive khác nhau:

```text
ToolInvocation
──────────────
Thời gian ngắn
Call API/DB/function
Cùng transaction context
Ví dụ:
- finance.get_summary
- crm.find_customer
- gmail.send
- vault.search


DelegationJob / ExecutionJob
────────────────────────────
Có thể chạy vài phút / lâu hơn
Durable
Có retry / lease / cancel / resume
Ví dụ:
- DeepSeek code repository
- Research mission
- Build application
- OpenSandbox execution
```

`ToolInvocationService` hiện rất phù hợp cho nhóm đầu. Nó đã có normalize input → policy → native/connector dispatcher → MCP capability bridge → output safety.

DeepSeek Harness nên thuộc nhóm thứ hai.

Nếu trộn hai thứ, sau này ADK sẽ rất khó phân biệt:

```text
tool đang chờ 300 ms
```

với:

```text
software engineer đang làm việc 20 phút
```

# 5. Mình không đồng ý với custom `BaseSessionService` trong proposal

Proposal đề xuất:

```text
session_bridge.py
custom BaseSessionService
  ↓
AgentRun
AgentEventRecord
mission_control_bus
```

với lý do tránh tạo thêm audit trail.

Ý tưởng “một canonical audit trail” là đúng, nhưng implementation này có nguy cơ phá một tính năng quan trọng của ADK.

ADK không dùng session chỉ để log chat.

`BaseSessionService` còn quản lý:

```text
session
state
event history
state delta
resume/replay
concurrency revision
```

Và Workflow 2.7 rebuild trạng thái node khi resume bằng cách scan session events.

Nếu tự viết `BaseSessionService`, OPC sẽ phải reproduce chính xác semantics của ADK về:

```text
state delta
temporary state
event ordering
stale session
replay
interrupt
checkpoint
workflow reconstruction
```

Rất dễ tạo bug khó thấy.

### Mình đề xuất ngược lại

Dùng native:

```text
ADK DatabaseSessionService
```

nhưng đặt trong vùng riêng:

```text
PostgreSQL

public/
  agent_runs
  agent_event_records
  tasks
  approvals
  outcomes
  ...

adk_runtime/
  sessions
  events
  app_states
  user_states
  adk_internal_metadata
```

Hoặc an toàn hơn nữa:

```text
opc_business database
opc_adk_runtime database
```

ADK native schema hiện dùng các tên khá generic như `sessions`, `events`, `app_states`, `user_states`, nên cần cô lập namespace.

Ownership sẽ là:

```text
ADK runtime DB
= checkpoint/replay/runtime state

OPC AgentRun + Event Ledger
= business state + canonical audit
```

Đây **không phải hai System of Record cạnh tranh nhau**.

Nó giống:

```text
Redis queue state ≠ business database
```

OPC chỉ cần project các ADK lifecycle event quan trọng sang canonical event ledger.

# 7. `ModelGateway` hiện chưa đủ contract để nối ADK

Proposal đúng khi muốn:

```text
ADK
 ↓
CosaModelGatewayLlm
 ↓
ModelGateway
 ↓
LiteLLM
```

Nhưng không nên triển khai LiteLLM invoker ngay với contract hiện tại.

Hiện `ModelGateway.invoke()` nhận:

```python
prompt: str
system_instruction: Optional[str]
invoker_fn(provider, model, prompt)
```

Nhưng `system_instruction` **không được truyền vào `invoker_fn`**.

Sau khi provider trả về, code lại:

```python
content=str(raw_res)
```

và token được ước lượng bằng:

```python
len(prompt.split())
```

Trong khi ADK `LlmRequest` thực tế chứa:

```text
contents[]
system_instruction
tools
tool declarations
response schema
generation config
...
```

và `LlmResponse` có:

```text
typed Content
function calls
function responses
usage metadata
finish reason
...
```

Nếu nối theo proposal hiện tại, sẽ mất hoặc méo:

```text
multi-turn messages
system prompt
function calls
tool schema
structured output
usage token thật
finish reason
provider metadata
```

### Nên refactor trước thành typed model gateway

Ví dụ:

```text

  system_instruction
  tools
  response_schema
  temperature
  max_tokens
  stream
  metadata

  content
  tool_calls
```

```text

 ↓
```

# 9. Hybrid Workforce: hướng đúng nhưng proposal nên sửa `AgentHierarchy`

Proposal phát hiện đúng rằng hiện có bốn khái niệm:

```text
Agent
AgentDefinition
AgentProfile
WorkforceMember
```

Đây thực sự là fragmentation.

`WorkforceMember` hiện vẫn FK vào legacy `agents.id`.

`AgentDefinition` lại sở hữu risk, capability, model config, hierarchy và tool permission.

`AgentProfile` mới là runtime composition thực tế với skills/tools/model/runtime.

Proposal chọn:

```text
AgentDefinition
 = canonical AI employee definition
```

Mình đồng ý.

Nhưng có một điểm mình sẽ sửa.

Proposal muốn giữ `AgentHierarchy` và nhập `AgentRelation` vào nó.

Điều đó phù hợp với AI↔AI, nhưng không đẹp khi OPC có:

```text
Founder (Human)
   ↓ manages
CFO Agent

Human CTO
   ↓ manages
AI Software Engineer

AI Researcher
   ↓ reports to
Human Product Lead
```

Do đó hierarchy doanh nghiệp nên ở **WorkforceMember**, không phải AgentDefinition.

Mô hình tốt hơn:

```text
AgentDefinition
= template/capability definition

AgentProfile
= runtime composition

WorkforceMember
= concrete employee identity

WorkforceRelation
= organization relationship
```

Ví dụ:

```text
AgentDefinition
CFO Agent Template
      │
      ▼
WorkforceMember #200
"CFO AI của MIVA"
      │
      ▼
WorkforceRelation
reports_to → WorkforceMember #1 Founder
```

Còn `AgentHierarchy` nếu giữ thì chỉ là **template topology**, không phải company org chart.

# 14. Self-host khả thi, nhưng `APP_ROLE` conditional router chưa đủ

Proposal định:

```text
APP_ROLE=full
APP_ROLE=central_control_plane
```

và conditionally mount routers.

Ý tưởng đúng.

Nhưng `main.py` hiện import tất cả năm domain router **trước khi include_router**:

```python
from app.founder_os.router import ...
from app.business.router import ...
from app.workforce.router import ...
from app.integrations.router import ...
from app.platform.router import ...
```

Nếu chỉ:

```python
if APP_ROLE == "...":
    app.include_router(...)
```

thì central process vẫn import toàn bộ business/workforce dependencies.

Tốt hơn:

```text
create_app(role)

full_main.py
central_main.py
```

hoặc app factory conditionally import.

Ví dụ:

```text
app/
  bootstrap/
    create_app.py
  full_main.py
  central_main.py
```

Deployment:

```text
uvicorn app.full_main:app
```

hoặc:

```text
uvicorn app.central_main:app
```

Attack surface và dependency graph lúc đó mới thực sự tách.

# 15. PostgreSQL 18: đồng ý

Proposal nói PG18 có native UUIDv7 là chính xác.

PostgreSQL 18 phát hành ngày **25/09/2025** và có native `uuidv7()` time-ordered. ([PostgreSQL][2])

Nâng:

```text
PG16 → PG18
```

là hợp lý nếu kiểm tra:

```text
pgvector
backup/restore
pg_upgrade
Docker image
extension compatibility
```

Nhưng mình sẽ **tách PG18 upgrade khỏi UUID PK migration**.

Hai thay đổi này không nên nằm cùng một release.

# 16. Phần mình ít đồng ý nhất: đổi toàn bộ BigInt PK sang UUIDv7

Về kỹ thuật: làm được.

Về cost/risk so với giá trị nhận được: mình chưa thấy đáng.

Proposal đang đánh giá blast radius hơi thấp khi nói chủ yếu 15 model dùng `SnowflakeIDMixin`.

Ngay những file mình đối chiếu đã thấy các model không dùng mixin nhưng vẫn sinh Snowflake trực tiếp:

```text
Organization
Department
WorkforceMember
Task
TaskDependency
ChiefOfStaff mission/outcome/event
...
```

Ngoài schema còn những đoạn:

```python
int(request.workspace_id)
int(request.parent_run_id)
```

trong runtime/delegation.

DeepSeek adapter hiện cũng dựa khá sâu vào integer run IDs.

Nghĩa là universal UUID migration sẽ chạm:

```text
PK
FK
Pydantic schemas
FastAPI params
Flutter models
JSON payloads
event payloads
idempotency keys
tests
worker leases
runtime request
sync protocol
central mappings
logs
scripts
fixtures
```

Trong khi Snowflake hiện đã cho OPC:

```text
distributed generation
offline generation
time ordering
compact 64-bit index
no DB round trip
```

UUIDv7 chủ yếu thêm:

```text
standard format
no node-id coordination
easier cross-system interoperability
```

Đáng có, nhưng chưa chắc đáng thay mọi PK.

# 17. Mình đề xuất Hybrid ID Strategy

Thay vì:

```text

```


API mới trả:

```text

```


# 18. Test UUIDv7 trong proposal cũng nên sửa

Proposal yêu cầu:

```text
sinh 10k UUID
→ toàn bộ tăng dần
```

Không nên dùng điều kiện này cho generator concurrent/distributed.

UUIDv7 là **time-ordered**, nhưng không đồng nghĩa với:

> mọi UUID từ mọi process phải strictly monotonically increasing.

Đặc biệt nếu nhiều process sinh cùng millisecond.

Test đúng hơn:

```text
version == 7
unique == 100%
timestamp decode hợp lệ
timestamp nằm trong expected window
ordering có temporal locality
DB index insert behavior tốt
collision test multi-process
```

Nếu implementation cụ thể cam kết monotonicity trong cùng process thì test thêm riêng invariant đó.

# 22. Nên sửa roadmap proposal theo thứ tự này

Nếu mình là người triển khai codebase này, mình sẽ điều chỉnh proposal thành **9 bước**:

1. **Khóa architectural contracts trước**: bật branch protection/ruleset cho `main`, required CI; thêm boundary tests cấm direct DeepSeek import ngoài runtime adapter, cấm model provider bypass ModelGateway và cấm tool execution bypass ToolInvocationService. `main` hiện chưa protected nên bước này có giá trị thực tế ngay.
2. **Refactor ModelGateway thành typed request/response** rồi mới thêm `LiteLLMProviderClient`; sau đó viết `CosaModelGatewayLlm` chuyển đổi đầy đủ ADK `LlmRequest ↔ ModelRequest ↔ LlmResponse`.
3. **Tạo ADK runtime persistence riêng** bằng native `DatabaseSessionService`, trong schema/database `adk_runtime`; thêm `RuntimeSession` ở OPC để map ADK/DeepSeek/Sandbox/Human sessions. Không viết custom BaseSessionService ngay.
4. **Extract deterministic CoS domain services** từ `chief_of_staff.py`: mission creation, risk policy, status transitions, approval, quality gate, synthesis input. Sau đó dựng `AdkCofounderWorkflow` bằng ADK Workflow/FunctionNode thay vì custom root BaseAgent.
5. **ADK delegation chỉ tạo RunStep + DelegationJob** thông qua `TaskBoardService`. DeepSeek chỉ chạy trong delegation worker. Khi job terminal, enqueue durable ADK resume command; bảo toàn exactly-once.
6. **Cut over CoS sang ADK** qua một application service rất mỏng; chạy golden/parity tests trên database side effects và event trail; sau khi xanh thì retire `ChiefOfStaffOrchestrator`. Không cần dual production orchestrator dài hạn.
7. **Hợp nhất Hybrid Workforce**: `AgentDefinition = AI template`, `AgentProfile = runtime composition`, `WorkforceMember = employee identity`, `WorkforceRelation = HUMAN/AI org chart`; permission dần target `WORKFORCE_MEMBER`; nối `Task.execution_mode` vào real dispatch.
8. **Tách deployment/database concerns**: pure Postgres; app factory `full`/`central`; local business DB, team business DB và central control plane được định nghĩa rõ. Sau đó nâng PG16 → PG18 trong một migration riêng.
9. **UUIDv7 triển khai additive trước** bằng `public_id UUIDv7` cho aggregate/cross-boundary entities. Chưa migrate tất cả BigInt PK. Chỉ xem xét universal UUID sau khi đo được nhu cầu thực và có migration inventory đầy đủ.

# Chốt lại proposal hiện tại

**Nên giữ:** OPC là System of Record; ADK là orchestrator; DeepSeek là execution runtime; một Governed Tool Gateway; PostgreSQL thuần; single-authority Local/Team mode; unified Human + AI workforce; self-host support; InsForge chỉ là optional generated-app capability.

**Nên sửa:** dùng **ADK Workflow Graph thật** thay vì tự orchestration bằng root BaseAgent; dùng **ADK native DatabaseSessionService** cho runtime state thay vì custom session bridge; ADK **không direct-call DeepSeek** mà enqueue `DelegationJob`; refactor `ModelGateway` trước LiteLLM; org hierarchy đặt ở `WorkforceMember`; tách central-control DB khỏi team business DB; và **không rewrite toàn bộ Snowflake PK sang UUIDv7 ở giai đoạn này**.

Nếu sửa các điểm này, mình đánh giá kiến trúc có thể lên khoảng **9/10 về tính khả thi**, đồng thời giảm đáng kể rủi ro phải “đập lại lần hai” sau khi ADK mission resume và Human Workforce bắt đầu chạy thật.
